# 安全に名前を変える仕組み

リネームはユーザーの元ファイルを書き換える操作なので、プレビューと取り消しを必ず持つ（Platform Architecture §6、§7）。加えて、社内の共有フォルダ（NAS、`\\server\share`、OneDrive）で使うことを初版から前提にする。ここでは事故の種類ごとに「困っていること → 決定 → 実装」を書く。

ほとんどはローカルのフォルダでも起こる。ネットワークでは **起こりやすくなる** だけなので、ローカルかどうかで処理を分けない。

---

## 1. プレビューの後に状況が変わる

**困っていること**：プレビューを見ている間に、ほかの人がファイルを動かしたり、同じ名前のファイルを置いたりする。プレビューの検査だけでは足りない。

**決定**：実行の直前に 1 件ずつ確かめ直す。確かめてから変えるまでの隙間も、**上書きしないリネーム** で塞ぐ。

**実装**：

- 各操作の直前に、元のファイルがあり、大きさと更新日時が読み込んだときと同じかを確かめる。違えば「読み込んだ後に変更されています」で失敗にする。
- リネームには `std::fs::rename` を使わない。Windows でも macOS でも **行き先にファイルがあると上書きする** ため。代わりに OS の「行き先があれば失敗する」呼び出しを使う。

| OS | 呼び出し |
|---|---|
| Windows | `MoveFileExW`（`MOVEFILE_REPLACE_EXISTING` を付けない） |
| macOS | `renamex_np(..., RENAME_EXCL)`。SMB などで `ENOTSUP` のときだけ、存在確認 → `rename` に落とす（ログに残す） |
| Linux（テストだけ） | `renameat2(..., RENAME_NOREPLACE)` |

## 2. 途中で失敗する

**困っていること**：接続が切れる、ほかの人が Excel で開いていてロックされている、権限が無い。1,000 件のうち 300 件目で止まると、半分だけ変わった状態が残る。

**決定**：失敗したらその場で止め、「変更した分を戻す / 飛ばして続ける / ここで終える」を選ばせる（[SPEC.md](SPEC.md) §7）。どの状態からでも戻せるよう、操作の記録（ジャーナル）を **先に** 書く。

**実装**：

- エラーは原因が分かる日本語にする。

| OS のエラー | 文言 |
|---|---|
| `ERROR_SHARING_VIOLATION`、`ERROR_LOCK_VIOLATION` | ほかの人が開いている可能性があります |
| `ERROR_ACCESS_DENIED`、`EACCES`、`EPERM` | 変更する権限がありません |
| `ERROR_NETNAME_DELETED`、`ERROR_BAD_NETPATH`、`ERROR_UNEXP_NET_ERR` | ネットワークの接続が切れました |
| `ERROR_FILE_EXISTS`、`ERROR_ALREADY_EXISTS`、`EEXIST` | 同じ名前のファイルがあります |
| `ERROR_FILE_NOT_FOUND`、`ENOENT` | ファイルが見つかりません（移動・削除された可能性） |

- ジャーナルの形は §ジャーナル。

## 3. 元に戻す前提が崩れる

**困っていること**：実行の後でほかの人が名前を変えたり、同じ名前のファイルを置いたりすると、単純に逆向きにリネームすると他人の変更を壊す。

**決定**：戻すときも 1 件ずつ確かめ直し、上書きしないリネームで戻す。戻せなかったものは一覧で知らせ、無理に戻さない（Platform Architecture §7「その後に手で変えたものを上書きしない」）。

## 4. Mac と Windows で日本語の表記がずれる

**困っていること**：macOS で付けた「ガ」「パ」などは、濁点が分かれた形（NFD）で NAS に保存されることがある。Windows からは同じ名前に見えるのに別の名前として扱われ、検索に掛からない、同じ名前のファイルが 2 つ並ぶ、といったことが起きる。

**決定**：

- 整形ルールに「日本語の表記をそろえる（NFC）」を置き、既定でオンにする。
- 衝突の検査では、名前を **NFC にそろえ、大文字小文字を無視して** 比べる。Windows と macOS の既定のファイルシステムはどちらも大文字小文字を区別しないため。

## 5. 使える名前が OS で違う

**困っていること**：macOS では `:` や末尾のピリオドを使えるが、Windows では使えない。社内はほぼ Windows なので、Mac で作った名前が共有フォルダで開けなくなる。

**決定**：実行する OS に関係なく、**Windows の基準** で検査する（[SPEC.md](SPEC.md) §6）。

**実装**：

- 名前の長さは UTF-16 で 255 まで。
- フルパスが 260 文字を超えるものは「注意」にとどめる。Rust の標準ライブラリは Windows で長いパスに自動で `\\?\` を付けるので、このアプリ自身は扱える。ほかのアプリで開けない可能性を知らせる。

## 6. 入れ替えと大文字小文字だけの変更

**困っていること**：`a.txt → b.txt` と `b.txt → a.txt` を同時に行う（入れ替え）と、どちらを先にしても行き先が埋まっている。`report.txt → Report.txt` は大文字小文字を区別しないファイルシステムでは「同じ名前がある」扱いになる。NFC にそろえるだけの変更も同じ。

**決定**：行き先がこの一覧の中のほかのファイルで埋まっているものは順番を並べ替え、輪になっているものと、大文字小文字・NFC だけの変更は **一時的な名前を経由する 2 段階** にする。それ以外は 1 回で変える（ネットワークでの往復を増やさない）。

**実装**：

- 一時的な名前は同じフォルダに `.<元の名前>.renamer-<8 桁>.tmp`。別のフォルダへ動かさない（同期フォルダで「削除と作成」に見えないように）。先頭が `.` なので、読み込み直しても一覧には出ない。
- 2 段階の後半で失敗したときは、飛ばしても終えても、一時的な名前から元の名前に戻す。戻せなかったものだけを「一時的な名前のまま残りました」と知らせる。
- 一時的な名前の段階もジャーナルに書き、途中で落ちても元に戻せるようにする。
- 順番の計算（依存の順に並べ、輪を見つける）は純粋関数にしてテストを厚くする。

## 7. 遅い

**困っていること**：共有フォルダは 1 件ごとの往復が遅い。数千件の読み込みや実行で、ウィンドウが固まると壊れたと思われる。

**決定**：読み込み、プレビューの計算、実行、取り消しはすべてバックグラウンドで行い、進捗と中止を出す（Platform UI §5）。

**実装**：

- 読み込みはフォルダ直下だけを `read_dir` で読む。Windows では一覧の取得と同時に大きさと日時が取れるので、1 件ずつ問い合わせない。
- プレビューの計算は rayon で並列にする。入力のたびに番号を振り、古い計算の結果は捨てる。
- 実行は順番に意味があるので並列にしない。

## 8. リンクが切れる（運用上の問題）

**困っていること**：ほかの人のショートカット、Excel のリンク、メールに貼ったパスが切れる。技術的には防げない。

**決定**：ネットワーク上のフォルダで実行するときは、確認ダイアログに一言添える。それ以上はしない。

**実装**：ネットワーク上かどうかは、Windows は `GetDriveTypeW` が `DRIVE_REMOTE` か UNC パス、macOS は `statfs` のファイルシステム名（`smbfs`、`afpfs`、`nfs`、`webdav`）で判定する。ステータスバーにも「(ネットワーク)」と出す。

## 9. 同期フォルダ（OneDrive など）

**困っていること**：リネームはそのまま同期されるので、ほかの PC で競合が起きることがある。オンライン専用のファイルを触ると、ダウンロードが始まるのではないかという心配もある。

**決定**：特別な処理はしない。1〜3 の仕組みで足りる。リネームはファイルの中身を読まないので、オンライン専用のファイル（Files On-Demand）でもダウンロードは起きない。読み込み時に大きさと日時を取るだけなら中身は読まない。

## ジャーナル

実行と取り消しの記録。`app_data_dir()/journal.jsonl` に 1 つだけ置き、次の実行で置き換える。

- **JSON Lines** にする。1 万件の実行で 1 件ごとにファイル全体を書き直すと遅いので、1 行ずつ追記する。
- 1 行目に見出し（形式の版、実行 ID、開始時刻、フォルダ、計画した操作の一覧）を書き、**fsync してから** 最初のリネームを始める。
- 操作が 1 つ終わるごとに `{"done": 12}` を追記する（戻したら `{"undone": 12}`）。2 段階の操作は段階ごとに書く。
- 1 行ごとの追記は OS に渡すところまで（アプリが落ちても残る）。fsync は見出しと最後だけにする。1 万件で 1 件ごとに fsync すると、それだけで数十秒かかるため。停電のときだけ、最後の数件の記録が抜けることがある。
- 最後に `{"end": "completed" | "stopped" | "undone"}` を書く。途中で切れた最後の行は読み飛ばし、改行を補ってから追記を続ける。
- 起動時に `end` の無いジャーナルがあれば、前回の実行が途中で落ちたとみなし、元に戻すかを聞く。
- 戻すときは、終わった操作を逆順にたどる。一時的な名前で止まっているものは元の名前へ戻す。

ジャーナルにはパスが入るが、ファイルの中身は入らない（Platform Architecture §8 と同じ扱い）。
